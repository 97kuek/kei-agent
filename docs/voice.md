# 声のレイヤと Stack-chan

- 机上で声で相談し、作業は Slack の Kei Agent がやる
- 仕組み全体は [`design.md`](design.md)、使い方は [`using.md`](using.md)、決まりは [`agents.md`](agents.md)を参照
- **声は OpenAI Realtime API に任せ、思考は手元のサブスクのエージェントに任せる**

| 図 | 何を描いているか |
|---|---|
| [voice.png](voice.png) | **いまの形。** 音の出し入れは Mac。Stack-chan は身体と顔で、HTTP で指示するだけ |
| [voice-future.png](voice-future.png) | **将来構想。** マイクとスピーカーも Stack-chan に移した形（2節の「完全 Stack-chan 化」） |

| | 誰がやるか |
|---|---|
| 聞く・喋る・間の取り方・割り込み | **Realtime API**（`gpt-realtime-2.1-mini`、声は `cedar`） |
| ふだんの会話・聞き返し・言い方 | 同じ |
| 依頼者のこと（予定・締切・様子） | **手元のデータを道具として渡す**（`tools.py`） |
| 研究・授業・仕事の**中身**を調べる | **選択済み provider の担当 agent**。声のセッションの外で動く |
| 作業そのもの | **Slack の Kei Agent**（選択済み provider）。`asks/` 経由 |
| 音の出し入れ | `ffmpeg`（手元。`audio.py`） |
| 身体と顔 | Stack-chan（**まだ買っていない**。`face.py`） |

**お金がかかるのは声の分だけ。** 考えるところは購読のまま（Codex と Claude）なので、
声で長く話しても、そこは増えない。

## 1. 何をどこでやるか

| 役割 | どこ | なぜ |
|---|---|---|
| 聞く・考える・喋る | **Realtime API** | STT・TTSを挟むと、その分遅れてしまうため、Realtime APIで音をそのままやりとりする |
| 音の出し入れ | **Mac**（`ffmpeg`） | マイクとスピーカーは手元にしかない |
| 依頼者のことを答える | **Mac**（`tools.py`） | モデルは依頼者を何も知らない。渡さないかぎり何も答えられない |
| 調べもの | **Mac** → 担当 agent | 研究・授業・仕事の中身は、声のセッションの外で選択済み provider の agent に聞く（数秒かかる） |
| 身体と顔 | **Stack-chan** | 画面を見ていないときに気づけるのが、机に置く理由。**音は通さない**（2節） |

**本体（Stack-chan）だけではできないこと**

- **文字起こし** … whisper tiny がモデル 75MB・実行時 約390MB。PSRAM は 8MB で、50倍足りない
- **日本語の音声合成** … ESP-SR の TTS は中国語・英語向け。日本語は実質 AquesTalk（有償）だけ
- **カメラと音声の同時** … `GC0308` にハードウェア JPEG が無く、圧縮が CPU に乗る。
  I2S の録音・再生・WiFi・推論が同じ MCU に集中し、**最初に壊れるのは音**
- いまは音が Realtime API と Mac の間を流れるので、Stack-chan に残る仕事は**身体と顔**だけになった。

## 2. ハードウェア

| もの | 決めたこと |
|---|---|
| 機種 | **M5Stack CoreS3** 系。Core2 はカメラが無く、マイクとスピーカーが排他で、M5-Bus のサーボ基板を付けるとマイクが潰れる |
| ファームウェア | **`karaage0703/stackchan-atama`**。`GET /face?expression=`（6種）、`GET /status`、`GET /setting?volume=`。`POST /play_wav` は**使わない**（声は Mac から出る） |
| 首 | パン・チルトの2軸。Grove 接続の Takao Base ＋ SG90×2（M5-Bus の基板はマイクを潰すので避ける） |
| 買い方 | 組立済みの M5 公式「M5StackChan」か、CoreS3 Lite からの自作 |

**買う前に作る**（Q35）。声が Mac と API の間で完結した時点で、Stack-chan が要るのは目と顔だけになった。

### Stack-chan は「音声端末」ではなく「身体と顔」

**会話の音は Stack-chan を通さない。** 通したくなるが、いまのファームでは通せないし、
通すと Realtime API に替えた利点が半分消える。

| 描きたくなること | 実際 |
|---|---|
| Stack-chan のマイク → Mac に音声ストリーム | **入力の口が無い**（`stackchan-atama` は `/status` `/play_wav` `/face` `/setting` `/capture` だけ） |
| Mac → Stack-chan のスピーカーに音声ストリーム | **ストリームではなくファイル**。`/play_wav` は wav を1つ投げる形で、40ms ずつ返る PCM を流し込めない |

`/play_wav` を会話に使うと、**割り込みが死ぬ**。投げ切った wav は途中で止められず、
「どこまで聞かれたか」も分からないので `conversation.item.truncate` に渡す値が作れない。
使うとしても、知らせの音や短い固定音声のような**補助**に留める。

ハードの側も重い。CoreS3 の内蔵マイクは弱く（外付け U089 が要る）、I2S の録音・再生・WiFi が
同じ MCU に集中すると**最初に壊れるのは音**。24kHz を双方向で流すのは、その一番厳しい条件になる。

### 完全 Stack-chan 化（将来構想。[voice-future.png](voice-future.png)）

やるなら**ファームウェアを書く**ことになる。

```text
Stack-chan のマイク → I2S → CoreS3 → WebSocket/PCM → Mac（Realtime API）
                                   ← PCM ← CoreS3 ← I2S → Stack-chan のスピーカー
```

`stackchan-atama` に乗る利点（PC を脳にする前提で作られている）を捨てる話なので、
**買って、いまの形で動かしてから決める**。順番は次のとおり。

| 段 | 形 | 状態 |
|---|---|---|
| 1 | 入出力とも Mac、Stack-chan は顔 | **いまここ**。割り込みが効く |
| 2 | 知らせの音だけ Stack-chan（`/play_wav`） | 買ったら試す。会話には使わない |
| 3 | 入出力とも Stack-chan | ファームを書く覚悟ができたら |

## 3. 3本の道

聞かれたことは、答えられる相手が違う。

| | 手元のデータ | Realtime API | 担当 agent |
|---|---|---|---|
| 何に答えるか | 予定・授業・会議・締切・Kei Agent の様子 | ふだんの会話、聞き返し、言い方 | 研究・授業・仕事の**中身** |
| どうつながるか | `get_schedule` / `get_status` の道具 | セッションそのもの | `ask_agent` の道具（選択済み provider の担当 agent） |
| 待ち | ほぼ0（手元にあるものを渡すだけ） | 会話のまま | 数秒。呼ぶ前に「ちょっと見てみるね」と言わせる |

**振り分けはモデルがやる。** 前は言葉で当てていて（`予定` が入っていたら今日の予定を返す）、
**「明日の予定」「今週の予定」「今日は何やったんだっけ」に全部今日の予定を答えていた**（実測）。
道具にすれば、いつのことかはモデルが引数で渡してくる。

**手元のデータは、本体が変わったときに押しておく**（聞かれてから取りに行かない）。
朝のまとめのときに**1週間ぶん、日付つきで**渡す（`schedule.VOICE_DAYS`）。
今日ぶんだけ渡していたのが、上の欠陥の原因だった。

**調べる相手は、この会話を聞いていない。** `ask_agent` に渡す問いは、それだけ読めば分かる
一文にさせる（「さっきのあれ」では担当 agent が答えられない）。

### 依頼は2段

作業の依頼は `propose_request` で**下書きしてから** `send_request` で渡す。
下書きだけでは何も動かないので、1回の聞き間違いで作業が動き出さない。
読み上げて確認するのはモデルの仕事（`live.INSTRUCTIONS` に書いてある）。

### モデルは `gpt-realtime-2.1-mini`

| | `gpt-realtime-2.1` | `gpt-realtime-2.1-mini` |
|---|---|---|
| 音声（1M トークン） | 入力 $32 / 出力 $64 | 入力 $10 / 出力 $20 |
| 1日10分・30日（1ドル=157円） | **月 2,400〜4,200円** | **月 900〜1,900円** |
| 公式が言う違い | — | 「a **distilled** reasoning model」。**instruction following と function calling が落ちる**。「まず大きい方で作り、煮詰めてから mini を試せ」 |

この作りは**道具を正しく呼べるかどうかに全部かかっている**（呼ばずに記憶で答えると、
「明日の予定」に今日の予定を答える欠陥が戻る）。既定は `gpt-realtime-2.1-mini` とし、通常 agent の
model/effort recipe を共有せず、Realtime の model は `gpt-realtime-2.1-mini` に固定する。

## 4. 本体（オーケストレーター）とのつなぎ方

向きで手段が違う。理由は「待たせたくないか」と「柵を1か所に保つか」。

| 向き | 手段 | なぜ |
|---|---|---|
| 本体 → 声のレイヤ（状態を伝える） | **A2A**。声のレイヤが A2A サーバーになり、本体が投げっぱなしで頼む | 別プロセスから SQLite を読むと、テーブルの形を変えるたび両方直す。返事は待たない |
| 声のレイヤ → 本体（依頼を渡す） | **ファイル**（`<state_dir>/asks/`。本体が数秒ごとに拾う） | 本体に受け口を作ると Slack の窓口が2つになり、柵と権限の判定が2か所に散る |

`docs/agents.md` の規約に全部そろえる。

| もの | 値 |
|---|---|
| エージェント名 | `voice` |
| パッケージ | `src/kei_agent_voice/` |
| ポート | `8790`（大学 8787、研究 8788、仕事 8789 の次） |
| launchd | `com.kei-agent.voice`（常駐） |
| ログ | `~/Library/Logs/kei-agent/voice-launchd.log` |
| 秘密情報 | `~/.config/zsh/local/kei-agent-voice.zsh`（`OPENAI_API_KEY`、`KEI_AGENT_STACKCHAN_URL`） |
| 合言葉 | 既存の `KEI_AGENT_A2A_TOKEN` |

### スキルは `notify` 1つ

本体が渡すのは**出来事だけ**。文と顔は声のレイヤが組み立てる。

| `kind` | いつ | 声のレイヤがすること |
|---|---|---|
| `schedule` | 朝のまとめができた | 手元に置く（喋らない）。道具が読む |
| `due` | 締切24時間前 | 喋る＋顔 |
| `working` | 依頼を受け取った（👀） | 顔だけ（喋らない。依頼のたびに喋るとうるさい） |
| `done` | 作業が終わった（✅） | 喋る＋顔 |
| `failed` | 止まった（⚠️） | 喋る＋顔 |
| `limited` | 契約の上限に当たった | 喋る＋`sleepy` |
| `awaiting` | 返事待ちになった（❓ 確認） | 喋る＋顔 |
| `listen` | App Home のスイッチ | マイクを開ける・閉じる |

**知らせは「聞く」が切でも喋る。** 通知のときだけ短命の Realtime API 接続を作り、1件ずつ順番に
読み上げて閉じる。この接続ではマイクを開かない。「聞く」が入なら、既存の会話接続をそのまま使う。

## 5. 顔

| Kei Agent の状態 | 顔 |
|---|---|
| ふだん | `neutral` |
| 聞き取れなかった | `doubt` |
| 終わった（✅） | `happy` |
| 止まった（⚠️） | `sad` |
| 上限に当たった | `sleepy` |

`angry` は使わない（Kei Agent が怒る場面がない）。肝は **✅ と ⚠️ で顔を変えること**。

カメラ（`/capture`）は**使わない**。静止画で圧縮が CPU に乗り、音と同時にやると音が切れる。
離席の判定もそれを前提にしていたのでやめた（マイクのスイッチで足りる）。

## 6. 会話と記録

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 会話の区切り | セッションは**60分で切れる**ので、そこで繋ぎ直す（履歴は消える） | API の上限。声の会話はそれより長く続かない |
| 記録 | 全文は `<agent_root>/overview/voice/<日付>.md`（30日で消える） | 読み返さない記録を増やさない |
| Slack に残すもの | **依頼だけ**（`🎤 声からの依頼` のスレッド） | 話した中身はファイルにある |

記録に使う文字は**音声から取る**（`response.output_audio_transcript.done` が Kei の分、
`conversation.item.input_audio_transcription.completed` が依頼者の分）。
入力の文字起こしは**別料金**だが、何を話したかの控えのために入れている。

## 7. 出力先とスイッチ

| 状態 | どうなる |
|---|---|
| App Home の「聞く」が入 | Realtime API に繋がって、話せる。保存値から再起動後も復元する |
| App Home の「聞く」が切 | **繋がない**（マイクを開けず、課金もされない）。**既定は切** |
| App Home の「知らせる」が切 | 本体が `notify` を送らない。**既定は切** |
| `OPENAI_API_KEY` が無い | 繋がらないが落ちない（理由をログに残す） |
| `KEI_AGENT_STACKCHAN_URL` があって `/status` が返る | 顔が変わる |

**マイクは、常には開けない。** 講義中に録られているのが落ち着かないし、繋がっているあいだは
喋ったぶんだけお金がかかる。聞きたいときだけ Slack から開ける。

「知らせる」と「聞く」は別に切り替える。知らせだけを受けるときは、通知時だけ接続して読み上げ、
マイクは開かない。

`config.toml` の柵（同時に動かす数、書き込み先、読ませない場所、基本の接続先）には触らない。

## 8. 誰の声を受け付けるか

- **判定しない**
- そのかわり、**依頼を渡す前に読み上げて確認する**（3節）

Slack は `KEI_AGENT_ALLOWED_USER_ID` で依頼者1人に絞っているが、声の依頼は `asks/` に
ファイルを置く経路で、本体はそのファイルを信じる（書けるのは自分だけ、という前提）。
Stack-chan を机に置くと、この前提は「その部屋にいる人なら誰でも」に変わる。
**人が来る場所に移すときは、ここを決め直す。**

## 9. コードの地図

`src/kei_agent_voice/`（本体とは別のパッケージ。試すのをやめるときに消しやすい）。

| ファイル | 何をするか |
|---|---|
| `app.py` | 立ち上げ。A2A の口（`notify`）と声のセッションを同じプロセスで持つ |
| `card.py` | 名刺（`notify` 1つ、ポート 8790） |
| `executor.py` | 本体から来た出来事を受けて、すぐ返す。`held` に手元のものを溜める |
| `events.py` | 出来事 → 喋る文・顔 |
| `session.py` | 繋ぎ目。マイクの開け閉め、知らせの取り次ぎ、控えの記録 |
| `live.py` | Realtime API とのやりとり（人格・声・道具・割り込み） |
| `tools.py` | モデルに渡す道具（予定・様子・調べもの・依頼） |
| `audio.py` | 音の出し入れ（`ffmpeg`）。**割り込みは鳴らしているプロセスを殺して実現する** |
| `handoff.py` | 選択済み provider の研究・大学・仕事 agent へ、内容確認を委譲 |
| `face.py` | 机の上のロボットの顔 |
| `journal.py` | 会話の全文の控え |

本体側に足したのは2つだけ。`src/kei_agent/voice.py`（出来事を投げる）と、
`src/kei_agent/ask.py`（依頼を受け取る。声のレイヤより前からある）。
