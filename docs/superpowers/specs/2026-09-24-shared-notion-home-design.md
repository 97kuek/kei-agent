# 共通 Notion ホームの設計

## 目的と境界

`Keitaro Ueki` ページを大学・研究・仕事を横断する入口にする。依頼者は今週の研究 Task と授業課題、Outlook の予定と課題締切、日ごとの Daily とレトプラをここから確認できる。研究エージェントは研究ホーム、大学エージェントは授業ホームを引き続き正本として編集する。仕事エージェントは Outlook を読むが、研究・授業 DB は編集しない。

親ページは**論理的な親**とする。既存の研究ホーム・授業ホームは物理的に移動せず、現在のリンクと連携スコープを維持する。親ページには両ホームへのリンクと、横断表示用のリンクドビューを置く。既存 DB を重複して作らない。全エージェントはハブの情報を利用できるが、必要な行を Kei Agent 本体が読み取って各 agent に渡す。研究・大学・仕事 agent に親ページ全体の Notion トークンや編集権限を直接渡さない。

対象の親ページは `3e54fb5d2d07808dbe29fdbe67a4de56`。研究ホームは `3de4fb5d2d0780b9a193f4604d5ea09c`、授業ホームは `3e14fb5d2d07805ab7b2c01aab6b39a7`。現在、親ページには両ホームへの mention と `今月の予定` DB がある。研究の `Task`、授業の `課題`、研究の `ノート` は稼働中で、ノートには Daily／振り返りが現時点で10件ある。同じ 2026-09-21 の振り返りが2件あるため、移行時に一意化して片方を失ってはならない。

## ページと DB の構成

親ページの `今週のタスク` に、研究 `Task` と授業 `課題` のリンクドテーブルを別々に置く。研究側は `期日` が今週かつ `状態 ≠ 完了`、授業側は `締切` が今週かつ `状態 ≠ 提出済み` の行を表示する。元の DB の行を編集するだけで両ビューへ反映される。表示名に `研究 Task`／`授業課題` を付け、見かけ上の「一つの DB」と誤解させない。相対的な「今週」フィルタを使い、週が変わるたびに手で日付を更新しない。

既存の `今月の予定` DB をカレンダーの正本として再利用し、表示名は `予定カレンダー` に整える。既存の `名前`・`日付`・`タグ` を残し、`出典`（Outlook／課題／手入力）、`出典 ID`（同期用の不変キー）、`元 URL`、`最終確認`、`同期状態` を追加する。手入力行を同期処理は更新しない。Outlook は件名・開始終了時刻・場所・元 URL だけを記録し、本文、Teams の参加情報、パスコード、メール本文は取り込まない。課題は課題名・締切・元の課題ページ URL を記録する。カレンダー行から元データへ戻れるようにする。

親ページに新しい `日別記録` DB を作る。1日1行とし、表示列は `日付`（YYYY-MM-DD を title とする）、`Daily`（短い要約）、`レトプラ`（短い要約）の順にする。並び替え用の `対象日` date、各 Slack URL、元ファイル、移行元 ID は裏側のプロパティとして保持する。全文は行のページ本文に `## Daily` と `## レトプラ` の二つの区画で保存する。同日同種の記録が複数あるときは、各記録のタイトルと元ページ URL を付けた小見出しを並べ、内容をすべて残す。要約は本文から決定的に生成し、2,000文字を超えない。空欄は未作成を意味し、「なし」という作り物の内容を保存しない。

## 同期と日々の処理

Kei Agent 本体の定期処理が、選択済み provider の仕事エージェントから今後30日分の Outlook 予定を、大学エージェントから授業 `課題` DB の締切を受け取り、親ページのカレンダーへ同期する。大学側には read-only の完全な課題スナップショットを返す A2A 契約を設ける。現行 `list-due` は Moodle ICS 由来で最大20件までしか返さず、手入力の課題も含まないため、カレンダーの完全同期には使わない。Outlook 側も取得の完全性が確認できない応答を成功扱いしない。各取得が完全に成功したときだけ、その出典の行を `出典 ID` で upsert する。出典 ID は Outlook 側の stable event ID があればそれを使い、なければ元 URL・開始時刻・件名から作る。課題は Notion 課題ページ ID を使う。同じ ID の再取得で行を増やさない。別出典の同名予定を勝手に統合しない。取得失敗・契約上限・接続切れ時は既存行を削除・上書きせず、同期状態と最終成功時刻で鮮度を見せる。成功した取得から消えた行も自動削除せず `要確認` とし、手入力行には触れない。既存 `今月の予定` の手入力行を保護する。

Daily とレトプラの定期処理は以後 `日別記録` の対象日行を upsert する。Daily の再実行は Daily 区画だけ、レトプラの再実行はレトプラ区画だけを更新し、相手の区画や利用者が追記した結論を消さない。レトプラの Slack スレッドに貼られた結論は同じ行のレトプラ区画へ追記する。前回以降の振り返りを Daily 材料に使う読み取り処理も新 DB を読む。ローカルの `daily/*.md` と `reviews/*.md` は現行どおり残す。

## 既存記録の移行

移行は明示実行する一回限りのコマンドとし、最初に読取り専用の監査レポートを出す。研究 `ノート` DB の `種類 = Daily` または `振り返り` の全行をページネーション付きで取得し、元 ID、対象日、種類、タイトル、本文、Slack URL、ファイルを manifest に記録する。日付がない行、同定できない区画、本文を読めない行があれば書き込み前に停止する。

適用時は新 `日別記録` の日付行へ内容をコピーし、各原本との本文一致、件数、Slack リンク、重複日を検証する。この時点で原本は削除しない。照合できた原本だけを親ページ配下の `旧 Daily・レトプラ記録` へ移し、元ページ ID／URL を保持する。移動 API が DB 行の本文や旧 URL を保持できない場合は移動せず、コピー済み行と未完了の監査レポートを残して停止する。研究ホームには旧 Daily／レトプラのリンクドビューを残さない。SQLite の既存 `notion_links` は、元 ID と新しい日付行 ID の対応を検証してから更新する。再実行は同じ日付行と移行元 ID を検知して重複コピーしない。復旧時には manifest と原本を使い、元の親とリンクの対応を戻せる。原本の削除・アーカイブはこの計画ではしない。

## アクセスと失敗時の扱い

研究ホーム用の Notion gateway は研究ホーム配下だけ、大学用の接続は授業ホーム配下だけに制限したままにする。横断ページの書き込みは Kei Agent 本体だけが行う。既存の本体用 `NOTION_TOKEN` に親ページを追加共有する前提とし、トークンを agent prompt、ログ、Slack へ渡さない。親ページへのアクセスがなければ共有が必要だと明示して停止し、研究ホームへ代替保存しない。仕事・大学の取得が失敗した場合、別 provider に自動で切り替えない。カレンダーの同期失敗は Daily／レトプラ保存を妨げない。日別 DB の保存失敗は成功と報告せず、ローカルファイルと Slack 投稿を残して再試行可能にする。

親ページや既存 DB の ID は事前に読み取りで確認する。同名 DB やビューが複数あれば正本を推測せず停止する。連携スコープを広げるために研究・授業ホームを親ページの子へ移さない。外部サービスへの書き込みは migration と通常同期の対象に限定し、Notion 以外の Outlook・Moodle の元データは変更しない。

## 検証と完了条件

テストでは、相対的な今週ビュー、出典 ID による upsert、手入力行保護、取得失敗時の無削除、日別区画の独立更新、同日重複記録の無損失、移行再実行の冪等性、結論追記、権限欠如時の fail-closed を確認する。既存の Daily／レトプラ・大学課題・仕事予定のテストも通す。実 Notion では、変更前後のスキーマ、ビュー、日別行数、移行元10件の本文と URL、研究・授業 DB の場所、同期サンプルを再取得して照合する。実 Outlook と課題の同期は外部書き込みを伴うため、対象期間と行数を事前表示してから適用する。

この設計の範囲外は、研究と授業の Task を単一 DB に統合すること、Outlook への予定作成・変更、Moodle の課題変更、過去 Slack 投稿の書き換え、元ページの削除である。
