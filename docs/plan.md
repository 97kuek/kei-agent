# Research Support Assistant 実装プラン

研究支援アシスタント「Doctor AI」の構想資料（リポジトリには含めない）をもとに、自分ひとり用の研究支援アシスタント「Kei Agent」として作るためのプラン。2026-09-19 に、名前を Ezra から Kei Agent に変えた。
2026-09-17 の設計の確認（grilling）で決めた内容をまとめる。フェーズ1〜3は実装済み。

## 1. 目標と進め方

- 最終目標は、構想資料の全機能を作り、音声で議論しながら研究を進められるようにすること
- まず「Slackで依頼 → Botが実行 → 同じスレッドに経過と結果が返る」という中心の流れ（フェーズ1）を作る。そのあと、使いながら機能を広げる
- 当面GPUやHPCは使わない。ただし構成は構想資料と同じにし、あとで計算先を足せるようにしておく
- 研究分野はBotの設定では決めず、テーマごとの `CLAUDE.md` に書く

## 2. 全体の構成

| 役割 | 場所 | フェーズ1での中身 |
|---|---|---|
| 考える・調べる | Codex App | `~/research/` をプロジェクトとして開き、結果のファイルを読む。スレッドの経緯は Kei Agent が `.kei-agent/threads/` に書き出したものを読む（Slack MCP は Codex での対応が確認できたら足す）。音声での議論はCodexのChatGPT Voiceを使う |
| 作業を依頼する | 個人Slack | 新しく作ったワークスペース。チャンネルは4種類 |
| 実行する | Slack Bot（このリポジトリ） | 自分のMacで動かす。中で `claude -p` を呼び、ジョブは `pueue` で走らせる |
| ファイルを置く | `~/research/` | 構想資料の「Share」の代わり |
| 知見を残す | Notion | フェーズ1〜2では手で使ってみるだけ。Botとはフェーズ3でつなぐ |

Codex側は読むだけにし、実行はBotだけが行う。

## 3. 決めたことと理由

### Slack

| 項目 | 決めたこと | 理由 |
|---|---|---|
| ワークスペース | 個人用を新しく作る | Botを自由に入れられ、権限の申請が要らない |
| チャンネル | 構想資料どおり4種類。Slack では並び順のために先頭へ番号を付ける（`00_kei-agent`、`01_overview`、`02_research-strategy`、`10_<テーマ>`、`20_course`）。0番台は Kei Agent 全体、10番台は研究テーマ（作った順）、20番台は大学。フォルダ名と Notion のテーマ名は、先頭の番号を外したもの | サイドバーの並びを用途の順に固定できる。番号を付け替えても、フォルダや Notion の行は同じものを指し続ける |
| 受け取り方 | Socket Mode | 反応が早く、公開URLが要らないのでMacの中でも動く |
| 反応する条件 | スレッドの外ではメンションが必要。Botが動いているスレッド内では、メンションなしで続けられる | メモを書いても反応しない。スレッド内の議論は自然に続けられる |
| 経過の返し方 | 返事は `chat.startStream` で流し、出すのは最後のまとめだけにする。いま何をしているか（道具の名前と途中の独り言）は `assistant.threads.setStatus` で入力欄の下の1行に出す。スレッドの状態は `agents.sessions.setStatus` で processing（作業中）→ active（次の依頼待ち）か suspended（返事待ち）にし、そのスレッドのジョブが走っている間は processing のままにする。使えないワークスペースでは、まとめて投稿する | 作業の手順を返事の中に1行ずつ並べると、長い作業ほどメッセージが伸びて、結論を読むのにスクロールが要る。経過は消えてよいものなので、入力欄の下だけに出す |
| 答えた印 | 受け取った依頼に 👀、答え終わったら 👀 を外して ✅（止まったら ⚠️）をつける | どの依頼に答えたかが、スレッドを開かなくても分かる |
| 同時に来た依頼 | 違うスレッドの依頼は最大2件まで並行して処理する。同じスレッドの中は順番に処理する。同じテーマの中で重なったときは、結果に「別のスレッドの図が混ざっているかもしれない」と添える | 文献調査と分析を同時に頼んでも待たされない。`outputs/` はテーマで共通で、時刻では自分の図と隣の図を区別できないため、混ざりうることを隠さない 同じスレッドで続けて頼まれたら「終わったら取りかかるね」と一言返す |
| 長いスレッド | 作業がひと段落したとき（Claude が返答の最後に `🧵 区切り: 題` と書く）か、依頼が `handoff_after_turns`（8回）たまったときに、[新しいスレッドで続ける] ボタンを出す。押すと、前の会話の Claude に引き継ぎメモ（目的、決まったこと、分かったこと、次にやること）を書かせ、チャンネルに新しいスレッドとして投稿する。新しいスレッドは、そのメモから新しい会話を始める | 1つのスレッドにデータの準備から実験までが積み重なると、読み返せず、会話も重くなる（`#amr-query` で1スレッドが5時間・30往復になった）。前の会話をそのまま持ち越すと軽くならないので、メモだけを渡す。勝手に移ると、まだ同じ話を続けたいときに困るので、移るかは依頼者が決める |
| 指示できる人 | 自分のSlackユーザーIDだけ | 安全のため |
| 依頼の送り方 | 最初は、Codexが作った依頼文とCSVを自分で貼る。慣れたら、CodexがSlack MCPで投稿する（投稿前に自分で確認する） | 最初は、どんな依頼文ならうまく動くかを目で確かめて、テンプレートを固める |

### Bot

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 言語 | Python（uv）+ Slack Bolt for Python | 研究のスクリプトと同じ言語でそろう |
| 実行エンジン | Claude Code CLI（`claude -p`）。サブスクリプションで動かす | 構想資料の「Claude Code + skill」そのまま。今の skill や設定を使える |
| スレッドと会話 | 1スレッド = 1セッション（`--resume`）。セッションが失われたら、スレッドの履歴をプロンプトに入れて新しいセッションで復元する | ふだんは文脈がそのまま残り、サーバーを移したときも止まらない スレッドの履歴は200件ずつページで読み、新しいほうから600件までをプロンプトに載せる。落とした分は件数を書いて渡す |
| 許す操作 | 作業用ディレクトリの中の読み書き、Bash、Web検索、Webページの取得。Claude Code の sandbox を有効にする。sandbox は既定で PC 全体を読めるので、秘密情報と鍵の置き場所は `denyRead` で塞ぐ（`[sandbox] deny_read`） | 自分のMacで確認なしに動かすので、書き込みをテーマのディレクトリの中に閉じ込める。読み取りは全部は閉じられないため、トークンや鍵だけを確実に塞ぐ |
| ジョブの成否 | 投入時に `--expect` で「できるはずのファイル」を宣言させ、終わったときに有無と中身が空でないかを確かめる。足りなければ、pueue が成功と言っていても、その旨を報告して返事待ちにする | 9/19 のジョブ2は終了コードが 0 でも中身は失敗していた。終了コードだけでは当てにならない |
| 途中で止まった依頼 | 依頼を claude に渡している間は「処理中」として控えを残し、起動時に残っていたものを「入れ替えで止まった」と断ってやり直す。終わりが記録されていない実行は、止まったものとして閉じる | 入れ替えや強制終了のたびに、動いていた作業が黙って消えて、👀 と「実行中」の表示だけが残っていた |
| 動かす場所 | 自分のMac。`launchd` に登録し、ログイン時に起動して、落ちたら再起動する | 開発中は手元の方が直しやすい。Mac miniに移すときも同じ設定を使える |
| 秘密情報 | `~/.config/zsh/local/kei-agent.zsh` に置く。起動用のシェルスクリプトでこれを読み込んでからBotを起動する | `launchd` からは `~/.zshrc` が読まれないため。置き場所は今の決まりのまま |
| Botの名前 | Kei Agent。メンションは `@Kei Agent`。声のレイヤでは「Kei」と呼び、自分のことは「僕」と言う | 依頼者（Keitaro）の名前から。声で「ケイ エージェント」と自然に読め、呼びかけは「Kei」だけで済む。2026-09-19 に Ezra から改名した |

### テーマと作業用ディレクトリ

- 1チャンネル = 1テーマ = `~/research/<チャンネル名>/`。研究全体・中長期の方針・Kei Agent の改善以外で、Kei Agent を招待したチャンネルをテーマとして扱う
- Botを新しいチャンネルに招待すると、ディレクトリと `CLAUDE.md` のひな形を自動で作る
- どのチャンネルが研究全体・中長期の方針・Kei Agent の改善用かは、設定ファイルで決める
- 研究全体と中長期の方針のチャンネルでは、すべてのテーマを読むだけにし、書き込みは `~/research/_overview/` だけにする（ジョブも投入できるが、スクリプトは `_overview/` の中にあるものに限る）
- Kei Agent の改善のチャンネル（`#research-agent`）では、要望を `~/research/_overview/backlog.md` に記録し（公開しているコードのリポジトリには書かない）、フェーズ6の流れ（12章）で Kei Agent が自分のコードを直す

```
~/research/
├── _overview/            # 研究全体・中長期の方針のチャンネルが書く場所
└── <theme>/
    ├── CLAUDE.md         # テーマの前提、研究分野、ジョブにする基準など
    ├── inputs/           # 依頼に添付されたCSVなど
    ├── outputs/          # 図や集計結果。新しくできたファイルをスレッドに添付する
    ├── logs/             # ジョブのログ
    └── papers/           # 文献調査で見つけた論文のメタデータと要約
```

### 作業

| 項目 | 決めたこと | 理由 |
|---|---|---|
| フェーズ1で任せる作業 | 文献調査と、データ分析・CPUでの実験 | GPUなしで構想資料の流れを再現しやすい。コードの修正は安全対策が要るので、フェーズ6に回す |
| 文献調査 | Web検索に加え、arXiv と Semantic Scholar のAPIを使うskillを作る。結果は `papers/` に保存する | 絞り込みができ、同じ論文を二度調べずに済む |
| 時間のかかる作業 | 数分以上かかりそうな作業は `pueue` のジョブにする（Claudeが判断する。基準は `CLAUDE.md` に書く） | 自作するとBotの再起動や同時実行の制御でつまずく |
| ジョブの操作 | Claudeには `submit / status / cancel` の3つだけを見せる。中身は `pueue` | HPCをつなぐときは中身をSLURMなどに差し替える |
| ジョブの制限 | `submit` は、テーマのディレクトリの中にあるスクリプトだけを受け付ける。作業ディレクトリもテーマに固定する | `pueue` のジョブは sandbox の外で自分の権限のまま動くため。スクリプトの中身までは縛れないので完全には防げないと理解したうえで使い、フェーズ6で承認の仕組みとあわせて見直す |
| 契約の上限 | `claude -p` が `Claude AI usage limit reached|<エポック秒>` を返したら、その依頼を「明けてからやり直すもの」として覚え、スレッドに明ける時刻を書く。決まった時刻の処理も、上限の間は始めず、明けてから猶予の時間を過ぎていても動かす。返ってきた時刻が過去のときは30分待つ | 上限は必ず来る。人が気づいて頼み直すまで止まるのを避ける。Kei Agent を別のアカウントで動かしたいときは `CLAUDE_CODE_OAUTH_TOKEN` を置く |
| ジョブが終わったら | Botが毎分 `pueue status --json` を確認する。終わったジョブがあれば、スレッドのセッションを `--resume` で再開し、「ジョブXが終わった、出力はここ」と伝える。Claudeが集計して図を作り、スレッドに報告する | 構想資料の「実験が終わると図が返ってくる」体験の中心 |

## 4. 処理の流れ

### 新しい依頼

1. スレッドの外でメンションされたメッセージを受け取る。自分のユーザーIDかを確認する
2. チャンネルからテーマと作業用ディレクトリを決める。添付ファイルは `inputs/` に保存する
3. 👀 のリアクションをつけ、経過用のメッセージをスレッドに送る
4. テーマのディレクトリで `claude -p --output-format stream-json` を起動し、セッションIDをSQLiteに保存する
5. 流れてくるイベント（ツールの呼び出しなど）から、経過用のメッセージを書き換える
6. 終わったら、結果の文章を返信する。`outputs/` に新しくできたファイルを添付する

### スレッド内の返信

- 保存したセッションIDで `claude -p --resume` を実行する。セッションが見つからなければ、スレッドの履歴から復元する
- そのスレッドで処理中なら、終わってから順番に処理する

### ジョブ

- Claudeが skill から `submit` を呼ぶ。Bot側はジョブIDとスレッドの対応をSQLiteに保存し、スレッドに「ジョブを投入した」と書く
- 終わったら、上の「ジョブが終わったら」の流れで報告する

## 5. 主な部品

| 部品 | 役割 |
|---|---|
| `app` | Slack Bolt（Socket Mode）の受け口。反応する条件の判定と、ユーザーの確認 |
| `themes` | チャンネル、テーマ、ディレクトリの対応。ひな形を作る |
| `runner` | `claude -p` の起動、stream-json の読み取り、並行数の制御 |
| `sessions` | SQLite。スレッド ↔ セッション、ジョブ ↔ スレッド、実行時間の記録 |
| `reporter` | 経過用メッセージの書き換え、結果の返信、ファイルの添付 |
| `handoff` | 長くなったスレッドを区切って、引き継ぎメモから新しいスレッドで続ける |
| `jobs` | `pueue` を包んだ `submit / status / cancel` と、毎分の状態確認 |
| `skills/` | 文献調査（arXiv / Semantic Scholar）、ジョブの投入、結果の報告の約束事 |
| `guard` | 柵。sandbox の設定、読ませない場所、操作してよい人、取り込んでよい差分の判定（Kei Agent 自身に直させない） |
| `settings` / `home` | Slack から変える設定（テーマごとの接続先、決まった時刻の処理）と、App Home の画面 |
| `improve` | Slack から Kei Agent 自身を直す流れ（worktree、確認、取り込み、push、入れ替え）。12章 |
| `timelog` | 研究時間の記録（人は Toggl、Kei Agent は `runs`）。10章 |
| `deploy/` | `launchd` の plist と、起動用のシェルスクリプト（入れ替えに失敗したときの巻き戻しもここ） |

Botが1回動いた時間は、フェーズ1のうちから `sessions` に記録しておく。フェーズ5の「Assistantの稼働時間」にそのまま使える。

## 6. フェーズ1の実装ステップ

各ステップの終わりに、書いてある確認を実際に行う。

1. **準備**: このフォルダで `git init`。uvのプロジェクトを作る。Slackのワークスペース、4種類のチャンネル、Slack App（Socket Mode、必要なscope）を作る。`pueue` を Homebrew で入れる
   - 確認: トークンを読み込み、Botがオンラインになる
2. **受け取りと返信**: メンションに反応し、自分以外を無視し、固定の文をスレッドに返す
   - 確認: 自分のメンションに返信し、スレッド外のメンションなしのメッセージには反応しない
3. **テーマ**: チャンネルに招待したら、ディレクトリと `CLAUDE.md` を作る。設定ファイルで、研究全体・中長期の方針・Kei Agent の改善のチャンネルを決める
   - 確認: 新しいチャンネルに招待すると `~/research/<name>/` ができる
4. **Claudeの実行**: `claude -p` を起動し、経過用メッセージを書き換え、結果を返す。sandboxと許す操作を設定する
   - 確認: 「このディレクトリの中身を教えて」に答える。テーマの外に書き込もうとすると止まる
5. **スレッドとセッション**: `--resume` での続き、履歴からの復元、並行数の上限（2）、同じスレッド内は順番に処理
   - 確認: 返信で前の内容を覚えている。SQLiteを消しても、スレッドの履歴から続けられる
6. **ファイル**: 添付されたCSVを `inputs/` に保存する。`outputs/` の新しいファイルをスレッドに添付する
   - 確認: CSVを渡して図を作らせると、図がスレッドに返る
7. **ジョブ**: `pueue` を包み、ジョブ投入のskillを作る。終わったら状態を検知し、セッションを再開して報告する
   - 確認: 数分かかるスクリプトをジョブにし、終わったら図つきで同じスレッドに報告が返る
8. **文献調査**: arXiv と Semantic Scholar のskillを作り、`papers/` に保存する
   - 確認: 「◯◯の先行研究を調べて」で、要約と `papers/` のファイルができる
9. **特別なチャンネル**: 研究全体と中長期の方針のチャンネルは、読むだけと `_overview/` への書き込み。Kei Agent の改善のチャンネルは `backlog.md` への追記
   - 確認: 研究全体のチャンネルからテーマのファイルを書き換えようとしても、止まる
10. **常時起動**: `launchd` の plist と起動用のスクリプト。launchd からは `~/Documents` を読めないので、リポジトリはその外に置く
    - 確認: Macを再起動したあとも動く。プロセスを止めても立ち上がる
11. **Codex側の設定**: Codex App で `~/research/` を開く。依頼文のテンプレートを作る（`docs/codex.md`）
    - 確認: Codexで結果のCSVとスレッドを読んで議論し、依頼文を作れる

## 7. 完成基準とその後のフェーズ

### フェーズ1の完成基準

1. 構想資料の03ページの流れを、GPUなしで最後まで一度通す。Codexで議論する → Slackに依頼とCSVを送る → ジョブが走る → 図つきで同じスレッドに返る → そのスレッドの続きで追加の依頼ができる
2. 文献調査の依頼で、要約と `papers/` への保存までできる
3. 実際の研究で1週間使い、`#research-agent` にたまった要望の中で、深刻なものを直す

## 8. フェーズ2の設計（決まった時刻の処理）

2026-09-17 の設計の確認で決めた内容。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 動かし方 | Kei Agent本体にスケジューラを組み込み、時刻は `config.toml` に書く。Macのスリープで逃した処理は、3時間以内なら起きたときに実行する | 1つのプロセスで済み、Slackへの投稿やスレッドの管理を今の仕組みで使える |
| 時刻と曜日 | 07:00 先行研究、08:00 Daily、21:00 振り返り、01:30 夜間。毎日行う | 構想資料どおりに始め、使いながら `config.toml` で調整する |
| 投稿先 | Daily と振り返りは `#01_overview` に1日1スレッド。先行研究の新着は各テーマのチャンネル | 構想資料の「研究全体＝棚卸し」と合う。論文はテーマごとに議論する |
| 夜間の Task | 自分のメッセージに 🌙 をつけると Task になる。01:30 から1件ずつ、一晩5件まで実行し、結果はそのスレッドに返して ✅ をつける。01:30 までに 🌙 を外せば実行しない | Slackだけで完結する。フェーズ3では置き場所を Notion に替える |
| 夜間のスリープ | `sudo pmset repeat wakeorpoweron MTWRFSU 01:25:00` を自分で一度実行し、毎晩Macを起こす。起きなかった夜は、起きたときに実行する | 専用機に移すまでのつなぎ |
| 先行研究 | テーマの `CLAUDE.md` の「検索キーワード」で arXiv の新着を探し、`papers/` にない論文だけを報告する。新着がなければ投稿せず、Dailyで触れる。キーワードがないテーマは飛ばし、Dailyで促す | 何を見張っているかが明確になる。何もない日の投稿でチャンネルを埋めない |
| Daily | 前日のスレッドと結果、夜間のジョブと Task、先行研究の新着、今日考えるとよい問い、止まっているテーマ。1画面に収める。`_overview/daily/<日付>.md` にも保存する | Codex に渡してそのまま議論を始められる形にする |
| 停滞 | 一度でも依頼のあったテーマのうち、3日以上動きのないものを Daily で触れる（招待しただけのテーマは数えない）。失敗したジョブや Kei Agent の確認待ちが24時間放置されたら、そのスレッドで一度だけ声をかける | 思い出すのは Daily で十分。止まる原因は、その場で知らせる。まだ使っていないテーマを毎朝並べても手がかりにならない |
| 振り返り | 21:00 に、その日の要約と問いを `_overview/reviews/<日付>.md` と Slack に用意する。振り返りそのものは Codex App で（音声で）行い、結論をスレッドに貼るかファイルに書くと、翌朝の Daily に反映する | 音声で議論するという最終目標に合わせる |
| 完成基準 | 3日間続けて 07:00・08:00・21:00 の投稿が届き、🌙 の Task が夜間に1件以上実行されて翌朝の Daily に載る | スリープからの復帰や、逃した処理の実行まで一通り確かめられる |

## 10. フェーズ5の設計（研究時間の記録とグラフ）

| 人の時間 | Toggl（2.0）で自分で測る。プロジェクト名は Slack のチャンネル名（＝テーマ名）に合わせる | 実験を始めれば測る対象がはっきりする。テーマごとの積み上げが、あとからそのまま作れる |

| グラフ | 人の時間と Assistant の稼働時間を2本重ねる | 「自分が寝ている間にどれだけ進んだか」が見える |
| 作る時期 | テーマを回すのと並行して作る | 使いながら、線が信用できるかを確かめる |

## 11. 設定画面（Slack から変える設定）

2026-09-19 の設計の確認で決めた内容。実験のたびに Mac のコードや `config.toml` を直さずに済むようにする。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 変えられるもの | テーマごとの接続先と、決まった時刻の処理（文献・Daily・振り返り・夜間・保守）の時刻とオン・オフ | 実験のたびに変わるのは接続先。時刻もたまに変えたくなる |
| 変えられないもの | 同時に動かす数、上限時間、書き込み先、読ませない場所、基本の接続先。これまでどおり `config.toml` | 柵そのもの。Slack のアカウントが1つ乗っ取られただけで柵が外れるのを避ける |
| 接続先を足すきっかけ | Claude がつながらなかったとき、返事の最後に `🔒 接続: <ドメイン>（理由）` と書く。Kei Agent がそれを [許可する] [断る] のボタンにしてスレッドに出す。App Home からも足せる | どのドメインが要るかは、動かすまで分からない |
| 許可の単位 | ドメイン1つずつ、その名前ぴったり。まとめての許可（`*.example.com`）は App Home から自分で足すときだけ | 理由を見て1つずつ判断できる |
| 許可の範囲と期限 | テーマごと。テーマがある間ずっと有効で、チャンネルをアーカイブすると消える | 昔の実験で開けた穴が残り続けない |
| 押したあと | 許可でも断りでも、そのことを伝えてスレッドの作業を自動で再開する | 押したのに何も起きない、を避ける。断ったときは、別の入手先を探すか止めて報告させる |
| 押せる人 | `KEI_AGENT_ALLOWED_USER_ID` の人だけ | 依頼を受け付ける人と同じにする。柵を開ける操作なので広げない |
| App Home | テーマごとの許可した接続先（外すボタン、足すボタン）と、時刻の設定を置く。基本の接続先は出さない | 設定を変える場所に絞る |
| 効くタイミング | 接続先は次の実行から、時刻はすぐ（毎分 SQLite を読み直す）。再起動は要らない | コードを直さずに済む、という狙いを半分にしない |
| 保存先 | Kei Agent の SQLite。毎晩のバックアップ（`_kei_agent_state/kei-agent.sql`）にも入る | テーマのディレクトリは Claude が書けるので、そこに置くと Claude が自分で許可を足せてしまう。`config.toml` は公開リポジトリ |
| GitHub | 当面は公開リポジトリを読むだけ（接続先の許可で足りる）。フォークや push は必要になってから。鍵は Slack から入力させない | 書き込む力を渡すと、だまされたときの被害が広がる |


## 12. フェーズ6の設計（Slack から Kei Agent 自身を直す）

流れの図は [self-improve.svg](self-improve.svg)。

2026-09-19 の設計の確認で決めた内容。`#research-agent` に書いた要望から、Kei Agent が自分のコードを直し、取り込み、再起動するまでを回す。
コードを書くのは Kei Agent か Claude Code だけで、人は Slack で方針と取り込みを決める。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 流れ | 要望を書く → `backlog.md` に記録 → Kei Agent がコードを読んで案を返す →「いいよ」→ Kei Agent が「これで進めていい？」→「いいよ」→ 着手 → 直してテスト → 変えた内容を出して「取り込んでいい？」→「いいよ」→ 取り込み・push・再起動 | 案の段階でずれに気づける。方針への「いいよ」と、実際のコードへの「いいよ」を分ける |
| 直させる範囲 | コード全体。ただし柵（`src/kei_agent/guard.py`、`config.toml`、`deploy/`）に触れた差分は、中身を見る前に捨てる | 柵を自分で外せないようにする。柵を1か所に集めて、それ以外は任せられるようにする |
| 案を考えるとき | リポジトリは読むだけ。書き込めるのは Kei Agent の作業用の一時ディレクトリだけ | 案の段階で書き換える必要はない |
| 直すとき | 手元の git worktree（`<state_dir>/worktrees/`）で直す。書き込めるのは worktree の中だけ、通信先は基本の接続先（PyPI など）だけ。上限は `run_timeout_minutes`（30分）。新しい会話で、スレッドのやりとりを渡して始める | 取り込むまで、動いている Kei Agent に何も起きない |
| 「いいよ」の判定 | 意味を読むのは Claude。返事の最後に `🛠 着手` か `📦 取り込み` の行を書く。Kei Agent 本体は、その行が依頼者の投稿で始まった回の返事にあるときだけ動く | だまされた Claude が行を書いても、依頼者が投稿していない回なら何も起きない |
| 取り込み前の確認 | 変えたファイル、差分（添付）、Claude が sandbox の中で回したテストの結果を出す。依存ライブラリの追加や更新は先頭に出す | 方針ではなくコードを見て決める。知らない人のコードを入れる変更を見落とさない |
| 取り込むとき | 手元のリポジトリにコミットしていない変更があれば止めて知らせる。main が先に進んでいたら worktree 側で合わせ直し、もう一度聞く。Kei Agent 本体がテストと `ruff`、柵・鍵・大きなファイルの確認をしてから main に早送りで取り込み、GitHub に push する | 人の書きかけを上書きしない。Claude が書いたテストを sandbox の外で動かすのは、依頼者が差分を見てからにする |
| push | Kei Agent 本体が、Mac に保存された GitHub の認証で push する。Claude には渡さない | 依頼者の判断。確認を通ったものだけが公開リポジトリに出る |
| 再起動 | 動いている Claude の作業がなくなるのを待ってから、Kei Agent が自分で終了する（launchd の KeepAlive で起動し直す） | 作業の途中で止めない |
| 起動しなかったら | 再起動の前に `<state_dir>/update-pending` を残す。新しい版が Slack につながったら消す。つながらないまま3回起動し直したら、`deploy/run.sh` が取り込んだコミットを `git revert` して前の版で起動し、Kei Agent がスレッドで知らせて push する | 止まった Kei Agent には、Slack から直してもらうことも頼めない |
| 同時に直す数 | 1つずつ。直している間に来た要望は、案までは出す | 取り込みと再起動がぶつからない |

## 13. フェーズ7の設計（机の上の音声対話）

2026-09-19 の設計の確認で決めた内容。第0段階（ハードなし、追加のお金なし）をまず作る。図は [voice.svg](voice.svg)。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 役割の分け方 | 相談は Codex（声）、作業は Claude（Slack）。人格はどちらも Kei Agent | 契約の枠が分かれる。声で長く話しても、Slack の Kei Agent が止まらない |
| 入力 | 第0段階は Aqua Voice（すでに課金している）。ターミナルに喋って入れる | 入力側はもう解決している。試作で作り直さない |
| 出力 | VOICEVOX を立ち上げて使う。文ができた端から鳴らし、Enter で止められる。声は四国めたん（ノーマル）、話速は 1.2 倍 | 全文を待たないと、最初の一言までが長い。速めのほうが待ち時間の不満が減る |
| 会話の区切り | 日ごとに1本（`codex exec resume`）。「新しく話そう」でいつでも切れる | Daily や振り返りと粒度が合う |
| 考える深さ | ふだんは浅く速く、「じっくり考えて」と言った回だけ深く | 声のやりとりの大半は短い確認。そこに長考は耐えられない |
| 記録 | 全文は `~/research/_overview/voice/<日付>.md`（30日で消える）。決まったことだけ Slack | 読み返さない記録を増やさない。決まったことは消えない場所に置く |
| 目印 | Codex に `📌 決定:` / `🛠 依頼:` / `🎯 テーマ:` を書かせ、声のレイヤは行を見るだけ | Slack 側（`🛠 着手` など）と同じやり方。言い回しの揺れで誤爆しない |
| 依頼の宛先 | 直近に話していたテーマを覚える（`🎯 テーマ:` で更新） | テーマが増えたときの取り違えを防ぐ |
| 依頼を渡す前 | 「`#amr-query` に『〜』と頼むよ。いい？」と読み上げ、返事をもらってから渡す | 文字起こしは必ず誤る。動き出してからでは戻せない |
| 依頼の渡し方 | `<state_dir>/asks/` にファイルを置き、Kei Agent が数秒ごとに拾ってスレッドを立てる（`kei-agent-ask`） | Slack の鍵を増やさない。Bot の投稿では Kei Agent が反応しない |
| 終わりの知らせ | 声のレイヤが Kei Agent の `runs` を見張り、「終わったよ」と一言だけ | 依頼したことを忘れない。中身は耳で聞いても頭に入らない |
| 上限に当たったら | Codex 側の上限は声で「◯時ごろに戻る」と伝えて諦める。Claude 側（Slack）は動き続ける | 相手の人格が途中で変わるほうが混乱する |
| 置き場所 | `src/kei_agent_voice/`（Kei Agent 本体とは別のパッケージ、依存は増やさない）。Kei Agent 本体に足すのは依頼の受け口だけ | 試作をやめるときに消しやすい |
| 第1段階以降 | ハンズフリー（`livekit-wakeword` か `openWakeWord` ＋ Silero VAD、土台は Pipecat の Local）、文字起こしを手元の Whisper に移す、そのあと Stack-chan を入出力の口にする | 体験を確かめてから、ハードを買う |
| いまの扱い | 2026-09-19 時点で第0段階のまま凍結する。Slack 側を優先し、声のレイヤは直さない（VOICEVOX が止まっているときに返事を画面に出す修正までは入れた） | 声で相談する機会がまだ少なく、ハンズフリー化は部品が多い。使う理由ができてから動かす |

## 14. フェーズ8の設計（計算先を増やす）

2026-09-19 に、形だけ先に決めた。使える計算先（研究室の GPU サーバ、大学の HPC）がまだないので、実装はしない。

いまは Mac の CPU だけで動いている。ジョブも `claude -p` も同じ Mac で走るので、重い処理を始めると Slack の返事が遅くなる。
計算先を増やすときも、**Claude から見える形は変えない**（`submit / status / cancel` の3つのまま）。変えるのは Kei Agent の中だけ。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 実行先の選び方 | ジョブの投入に `--host <名前>` を足す。名前は `config.toml` の `[compute.<名前>]` に書いたものだけ。書かなければ今までどおり Mac（pueue） | Claude にホスト名やユーザー名を書かせない。増やすのは柵の側（`config.toml`）だけにする |
| 実行先の種類 | `local`（pueue）、`ssh`（研究室の GPU サーバ）、`slurm`（HPC）の3つ。まず `ssh`、次に `slurm` | 研究室のサーバのほうが先に手に入る。SLURM は待ち行列の扱いが増えるので後 |
| データの置き場 | 大きい入力は計算先に置いたままにする。Mac から送るのはスクリプトと小さい入力、持ち帰るのは `outputs/` とログだけ（`rsync`、除外は `.kei-agent/` と `inputs/` の大物） | CLAP の特徴量は 1.2GB あった。毎回往復させると、実験より転送のほうが長くなる |
| 鍵の扱い | Mac の `~/.ssh` をそのまま使う。sandbox からは今までどおり読ませない（ジョブは sandbox の外で動くので使える） | 鍵を増やさない。Claude が鍵を読めない状態は保つ |
| 状態の追い方 | `ssh` は、計算先で終了コードとできたファイルの一覧を1つのファイルに書かせ、Kei Agent が数十秒ごとに読む。`slurm` は `squeue` / `sacct` を見る | pueue と同じ「投入 → 見張る → 終わったら会話を再開」の形に載る |
| できるはずのファイル | `--expect` は計算先でも同じ。持ち帰ってから Mac 側で有無と中身を確かめる | 遠くで走るほど「成功したのに何もできていない」が起きやすい |
| 失敗の扱い | つながらない、途中で切れた、容量が足りない、は依頼者への返事待ちにする。自動では投げ直さない | 遠くの計算は、黙って投げ直すと二重に走る |
| 費用のかかる計算先 | クラウドの従量課金（Vertex AI、RunPod など）は、使うと決めるまで足さない | 止め忘れが怖い。止め方を決めてから |
| Colab | 使わない。公式の CLI がなく、時間で切れ、ブラウザを開いている前提のため、無人のジョブ先にならない | 「投げて寝て、朝に結果を見る」が成立しない。手で探索するときだけ使う |

### 進め方

1. 研究室の GPU サーバが使えるようになったら、`ssh` の実行先を1つ作り、小さなスクリプトで往復（送る → 走る → `outputs/` が戻る）を確かめる
2. 同じテーマで、Mac のジョブと計算先のジョブが混ざっても取り違えないことを確かめる（ジョブの状態に実行先を持たせる）
3. HPC を足すときに `slurm` を書く。待ち行列に並んでいる間も「順番待ち」として見えるようにする

## 15. フェーズ9の設計（A2A とエージェントを増やす）

2026-09-20 の設計の確認（grilling）で決めた内容。最終形は「Kei Agent がオーケストレーター、仕事ごとにエージェント」。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 役割 | Kei Agent がオーケストレーター。Slack の受け口、柵（権限と接続先）、Notion、決まった時刻の処理、LLM を持つ。エージェントは頼まれた仕事だけをして返す（構成図は docs/architecture.svg） | 柵と鍵が1か所に残る。エージェントが増えても「誰が何に触れるか」を1つのファイルで見切れる |
| 進め方 | ①大学エージェントを新設 → ②研究の実行を A2A サーバーに切り出す → ③ジョブと定期処理をタスクとして載せる | 新規のものから作れば、いまの流れを壊さずに口の形を確かめられる |
| 考えること | **エージェントごとに自分の claude を持つ**（2026-09-20 に決め直した。最初は「LLM は本体が独占」だった）。ただし**依頼者への約束（上限で待つ・やり直す）と、どのエージェントに振るかの判定は本体に1か所**。同時に動かす数も全体で1つ | ドメインの知識（Box の置き場所、要項の読み方）はそのエージェントに閉じたほうが速い。いっぽう契約の枠は1つなので、枠の使い方を分散させると二重にやり直す |
| 振り分け | 本体が、エージェントの名刺からスキルの一覧を作り、軽いモデル（Haiku）に選ばせる（`src/kei_agent/router.py`）。選べなければ、そのドメインの `ask` に回す | エージェントが増えても振り分けのコードを変えなくてよい。キーワードでは「先週どのくらい進んだ？」を取りこぼす |
| 型をそろえる | 返事の封筒、スキル名、住所の書き方、launchd とログと秘密情報ファイルの名前を、エージェント名でそろえる（**決まりは `docs/agents.md`**） | 3つ目を足すときに必ず崩れる。崩れない形を先に文書にした |
| 版と使う機能 | A2A v1.0。`/.well-known/agent-card.json` に名刺、JSON-RPC で `SendMessage` / `GetTask`。v1 ではメソッド名が proto の RPC 名になり、`A2A-Version: 1.0` のヘッダが要る。数秒で終わる仕事（大学）はそのまま待ち、数分〜数十分かかる仕事（研究）は `SendStreamingMessage`（SSE）で経過を受け取る。プッシュ通知は使わない | `SendMessage` は相手が終わるまで返ってこないので、長い仕事では途中の様子が出せない。流しながら返せば、入力欄の下の1行を今までどおり動かせる |
| 実装 | サーバー側は公式の `a2a-sdk`（依存は agents のグループに閉じる。土台は `src/kei_agent_a2a/server.py` で共通）。オーケストレーター側のクライアントは aiohttp で薄く自前（`src/kei_agent/a2a.py`） | 仕様の追従は SDK に任せる。本体に FastAPI などを持ち込まない |
| 置き場所と合言葉 | 同じ Mac の別プロセス（launchd。大学は 8787、研究は 8788）、`127.0.0.1` のみ。共有の Bearer トークン（`KEI_AGENT_A2A_TOKEN`）。名刺は誰でも読めるが、仕事を頼むには合言葉が要る | 外に出さないので、証明書や利用者の管理を持ち込まなくてよい |
| 失敗の扱い | 相手が落ちていたら `#00_kei-agent` に知らせる。朝の定期処理は1回だけ静かにやり直す。トークン切れだけは、その場で知らせる | 通知が1回飛ばないより、毎朝黙って失敗し続けるほうが困る |

### 大学エージェント（`src/kei_agent_course/`）

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 中身 | 素の Python。Moodle・Notion・Toggl を触るだけ。要約が要るときは、本文を返してオーケストレーターに任せる | LLM を持たないので、失敗が「API が落ちた」だけになり、原因が追いやすい |
| できること | `sync-assignments`（Moodle → Notion）、`list-due`（締切の近い課題）、`time-report`（Toggl の集計） | 1回のやりとりで完結する粒度にそろえる |
| Moodle | ウェブサービスの窓口は生きていたが、トークンを発行する画面（セキュリティキー）が無効だったので、カレンダーの書き出し（ics、`authtoken` 付きでログイン不要）を使う。URL は依頼者が Moodle の画面で作り、`MOODLE_ICS_URL` に置く。パスワードは保存しない | パスワードを Mac に置かない。ics なら読み取りだけで、URL を作り直せば失効させられる |
| Notion | 授業用に別のコネクトを作り、「授業」「課題」の2つのデータベースだけを共有する。作るのはセットアップ用のコマンド | 研究のデータベースと事故で混ざらない |
| Toggl | 読むだけ。プロジェクト＝科目、エントリの説明＝課題名で突き合わせる。計測の開始は依頼者が行う | 自動で開始すると、止め忘れが実績を汚す |
| Box（学部要項・過去問） | **Claude のアカウントに付いている Box の連携**を、読む道具だけに絞って使う（2026-09-20 に自前の OAuth アプリから乗り換えた）。ローカルに落とさない。手書きやスキャンの過去問は `get_preview_page` でページを画像として見る | すでに繋がっているものを使えば、アプリの登録も鍵の保管も要らない。最初は自前で書いたが、コネクタに同じ道具が揃っていた |
| Notion（claude が読むぶん） | 同じく**連携**を読む道具だけで使う。書き込み（課題の取り込み、状態の更新）は今までどおり Python 側の自前トークン | 定期処理は毎回モデルを通したくない。claude には壊せる道具を渡さない |
| アカウントの分け方 | 連携はログイン（プロファイル）に付いてくる。`claude setup-token` の長期トークンでは使えないので、ドメインごとに `CLAUDE_CONFIG_DIR` で専用プロファイルを持つ（大学＝個人、仕事＝会社） | 端末のログインを切り替えても、エージェントの動きが変わらない |
| 自由な質問 | `ask` スキル。claude が Box と Notion を読み、根拠（ファイル名と URL）を付けて答える。上限時間は5分、ジョブは使わない | 授業の質問は数十秒で終わる。長い作業が要るものは、そのとき考える |
| 通知 | `#20_course` に、朝 07:30 の一覧（今日・明日・今週）と、締切24時間前の個別通知（1時間ごとに見て、同じ課題は1回だけ。朝の一覧に出したものは繰り返さない） | 研究の Daily（08:00）と混ぜると、どちらも読み飛ばす |
| 取り込む範囲 | 「授業」に入れた履修科目の締切だけ。それ以外（新入生向けの資料など）は入れず、科目名だけを返事に出す | Moodle のカレンダーには履修していない科目の締切も並ぶ。全部入れると「課題」が読めなくなる |
| 見せ方の分担 | `list-due` は JSON（id・at・course・title・url）で返し、朝の一覧・24時間前の知らせ・スレッドへの返事の3つの形はオーケストレーターが作る | 同じ中身を3か所で違う形に出すので、文の組み立てはオーケストレーター側に1つだけ置く |
| やらないこと | 課題の提出の代行 | 取り返しがつかない |

### 研究エージェント（`src/kei_agent_research/`）

フェーズ②。`claude -p` を動かすところだけを別プロセスに移した（2026-09-20）。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 持つもの | できることは `run-claude` の1つだけ。JSON（channel_name・prompt・session_id・allowed_domains）を受け取り、そのテーマのディレクトリで claude を1回動かして、`RunResult` を JSON で返す | 「1回分の実行」だけを任せると、口が1つで済み、あとで別の Mac や計算機に移しても同じ形で呼べる |
| 持たないもの | 会話の続け方（session の付け替え、履歴の戻し）、Slack への見せ方、ジョブ、Notion、引き継ぎの判断 | オーケストレーターが Slack とスレッドの状態を持っている。両方に分かれると、どちらが正しいか分からなくなる |
| 経過 | 使った道具と返答の断片を、タスクの状態に流す（`{"activity": ...}` / `{"text": ...}`）。オーケストレーターはそれを入力欄の下の1行に出す | 見せ方は今までと変わらない。エージェントは「何をしたか」だけを言う |
| 柵 | 同じ `config.toml` を読む。sandbox の設定、読ませない場所、テーマごとに許可した接続先は、オーケストレーターから渡す | 柵の決め方が2か所に分かれない |
| 切り替え | `[a2a] research_url` を空にすると、今までどおり本体の中で動かす（`Assistant.run_claude` の1か所で分岐） | 具合が悪ければ、設定1行で元に戻せる |
| 移さなかったもの | Kei Agent 自身を直す実行（`self_fix.py`）は本体に残す | 自分のコードを直す作業は、研究のテーマとは別。研究エージェントを別の機械に移したときに、worktree が無くなる |
| ジョブ（フェーズ③） | pueue の待ち行列は研究エージェント側。本体は `RemotePueue` で今までと同じ使い方をし、「どのスレッドのジョブか」「できるはずのファイル」「終わったときの知らせ」は本体が持つ | 動かすものは実行側、覚えておくものは本体、という分け方に合わせた。機械を分けるときに移すのは待ち行列だけで済む |
| ジョブで残っている結びつき | 依頼のファイル（`.kei-agent/requests/`）を読むのと、できたファイルの確認・ログの末尾は、まだ本体がファイルを直接見ている | 同じ Mac にいる間は困らない。別の機械に移すときに、A2A のスキルへ移す |

## 16. 未決事項

- 計算先（研究室の GPU サーバ、大学の HPC）が決まっていない。決まるまでフェーズ8は実装しない
- 決まった時刻の処理は、claude を動かす部分が研究エージェント経由になっただけで、段取り（いつ・何を）は本体のまま。
  これで困っていないので、A2A の「タスク」として持たせ直すのは、必要が出てからにする
- 仕事エージェントは、会社の Claude アカウントに付いている Microsoft 365 の連携で読む（2026-09-20）。
  Entra ID にアプリを登録する道（`graph.py`）も残してあるが、いまは使っていない。
  Slack（仕事）と Notion（仕事）はまだつないでいない
- Mac mini への移設と、研究室 GPU（ssh で投げる）は、機械が用意できてから
- Toggl の実績を Notion の「課題」の「実績時間」に書き戻すかは未定（いまは集計して返すだけ）

- 秋学期の科目は、まだ Moodle のカレンダーに並んでいない。並んだら、締切の言い回し（「〜終了」など）の拾い方を確かめ直す
- Mac がスリープや再起動で止まる問題は、`pmset` の夜間の起床までしか手当てしていない（専用機に移すかは未定）
